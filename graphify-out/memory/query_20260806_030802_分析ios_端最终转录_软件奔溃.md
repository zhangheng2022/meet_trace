# Q: 分析ios 端最终转录 软件奔溃

## Answer

Expanded from original query via vocab: [ios, finalization, transcription, asr, sensevoice, sherpaonnxasrengine, audio, memory, native, crash, dispose, isolate]. 高置信主因是 iOS 最终转录默认并行启动 SenseVoice ASR 与说话人分离，而生产组合根在 2026-08-05 的 dd108bb 中重新启用了 sherpa_onnx 1.13.4 OfflineSpeakerDiarization。该版本 process/processWithCallback 对完整 Float32 波形 calloc 后未 calloc.free，30 分钟至少泄漏 115.2MB 原生堆；应用 worker 同时保留另一份完整 Dart Float32 波形。并行加载约 239MB SenseVoice 模型、约 41MB 说话人模型和 ONNX 工作区会形成高内存峰值。录音结束时预览 SenseVoice Engine 的 dispose 又是 unawaited，详情页会立刻启动最终转录，可能短暂重叠两个 SenseVoice recognizer 加分离器。iOS 风险监控仅报告 memoryPressure unknown，不会阻断。无 .ips/Jetsam 日志，不能最终区分 Jetsam/OOM 与原生 EXC_BAD_ACCESS；关闭全局说话人分离后复测是最快判据。
